Usage cadencer (pace)

Keeps usage on pace with the weekly quota (axis wk) and the 5 h window (axis 5h): it measures and, if you ask, adds a short pause before each tool call. It never switches model or effort.

  • Heavy Pro/Max use: a gauge with limits for the 5 h and weekly windows.
  • Many fronts at once: parallel agents share one steady cadence.
  • Same quota, other tools: heavy Desktop/Design slows Claude Code.
  • Fewer stalls: the pause grows before the 5 h window hits the ceiling.
  • Weekly reserve: spreads the week over business days, 5% kept.
  • One account: all sessions and subagents count together.
  • Predictable cost: pauses stay under the cache TTL.
  • See first: pace measure shows the cut, pauses nothing.
  • Your control: off by default, manual step, fail-open.

How pace changes the curve

Illustrative model, not measured data

Pace delays calls; it does not reduce the tokens a task needs. The same work finishes later than an unrestricted burst, but without hitting the ceiling and stalling until the reset; by the reset both curves have used about the same share of the window. The gain depends on how much of the window you use: well below the ceiling there is little to gain. A marks when the same task set finishes in each chart.

Install

Requirements: Claude Code 2.1.80+, Pro or Max plan (an API key gets no usage data), Python 3 on PATH. No plugin published yet: manual install, 4 steps.

1 · Files

Copy to the machine's ~/.claude: hooks/pacing.py and commands/pace.md. config/pacing.config.json is optional.

2 · Hooks

Merge into the hooks block of settings.json, keeping the existing ones. The PreToolUse timeout of 60 is required.

JSON of the 4 hooks 
"hooks": {
  "PreToolUse": [
    { "matcher": "*", "hooks": [ { "type": "command",
      "command": "python -S \"$HOME/.claude/hooks/pacing.py\" enforce", "timeout": 60 } ] }
  ],
  "UserPromptSubmit": [
    { "hooks": [ { "type": "command",
      "command": "python -S \"$HOME/.claude/hooks/pacing.py\" prompt", "timeout": 5 } ] }
  ],
  "SubagentStart": [
    { "hooks": [ { "type": "command",
      "command": "python -S \"$HOME/.claude/hooks/pacing.py\" agent-start", "timeout": 5 } ] }
  ],
  "SubagentStop": [
    { "hooks": [ { "type": "command",
      "command": "python -S \"$HOME/.claude/hooks/pacing.py\" agent-done", "timeout": 5 } ] }
  ]
}

3 · How pace gets usage (pick one)

The status line is the only source of usage (rate_limits). Run the command in a new session; each backs up settings.json and never overwrites a status line that is not pace's.

A · With the segment in the status line
pace setup

Writes a statusLine with layout L1 (model, usage, cadence). If you already have one, it keeps yours and shows how to chain the segment.

B · Without changing the status line
pace setup silent

Writes a statusLine that prints nothing: pace only collects usage. State is in pace status and pace brief.

Already have your own status line? Nothing is touched: the command prints the line to add to your script:

python -S "$HOME/.claude/pace/pacing.py" statusline --record-only >/dev/null

4 · Turn on

pace on

Until the first sample (after the session's first reply) pace status says no usage data. If it persists: Claude Code version, a plan without rate_limits, or a status line overridden by settings.local.json.

Now: steps

Recommended pause × step, capped at cap_s. Effect on 25 s:

Calibrate r

r = Δweek / Δ5h: if the week rose 2% while the 5 h window rose 20%, r = 0.1. pace shows Δ5h per window.

config/pacing.config.jsonDefaultWhen to change
hours / workdays[0,24] / [0..4]Set it to your real window (e.g. [9,19]). With [0,24] nights count and the needed rate is ~3x low for someone working 8 h/day.

How it decides

LevelWhenDoes
okDeviation ≤ 2% and no 5 h deficitNothing.
L1Ahead of budgetPause min(cap, deficit × k) per turn; 0 with no recent use.
L2Pause at the cap for 2 decisions; drops after 15 minKeeps the pause and denies subagents above n_max.
L35 h window ≥ 95%Pause at the cap; does not deny calls.
  • Current cadence = Δ5h × r ÷ hours (% of the week/h). Needed = daily budget ÷ active hours. Cut = 1 − needed ÷ current.
  • 5h axis: needed = (95% − used) ÷ hours to reset; deficit = largest Δ5h − needed × time of the five windows. It pauses only if the pace would exhaust the window before reset.
  • Budget = 95% × elapsed business days ÷ 5 (Thursday to Thursday, 06:00 BRT). Weekend use lowers the weekday budget.
  • Two axes: the larger pause wins, not the sum. Usage from different sessions is merged by a monotonic envelope: a stale reading from an idle session does not count.
  • Window reset: when the 5 h window resets (or the week turns) its old reading is dropped at once: level 3 and the 5 h pause end, the status line draws the window as 0%, and the decision is recomputed without waiting 30 s. A manual step (manual x…) survives the reset; pace auto clears it.

Guarantees and limits

Guarantees

  • Off by default; with no ctl.json the hook exits without acting.
  • An error, stale data or missing rate_limits lets the call run.
  • Pause ≤ cap_s (max 55 s) and, per turn, below cache_ttl_s − cache_margin_s (210 s): the cheap cache keeps hitting.
  • A window that already reset never keeps a pause.
  • Volatile state in %TEMP%\claude-pacing, pruned at 40 min.

Limits

  • The pause delays consumption; it does not cut tokens per task.
  • Usage from other tools (Claude Desktop/Design) shows up only when a Claude Code session gets a reply.
  • Every tool call and every status line refresh starts a Python process (~83 ms).
  • 1% resolution: ~3 min on the 5 h window, ~1.2 h on the week.
  • Tested by unit and process tests; not yet exercised live in a working session.
Reference

Remove

  • Pause: pace off.
  • Clear state: delete %TEMP%\claude-pacing.
  • Fully: remove from settings.json the 4 hooks that call pacing.py and pace's statusLine; delete commands/pace.md and ~/.claude/pace/.
